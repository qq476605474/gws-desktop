# gws — GWS

多仓库需求开发管理：拉代码、合环境、提 MR、写文档。一个需求一个工作区，全程不切分支。

## 执行纪律（最高优先，先读这一节）

这个技能替用户操作的是**真实需求工作区**。界面上有约束的地方，命令行同样有；
不要为了“把命令跑通”自己编一个值出来。

1. **所有字段都先问一遍，包括选填。** 用户只说了“建个需求”时，把分支名/后缀、
   需求名称、分类、模块、基线**逐项问完**；选填项要写明“不填用默认”以及默认是什么
   （如“模块不选就只挂文档库”），由用户决定，不要静默采用默认值。
   不要拿聊天内容里的零散词自己拼。
2. **枚举值必须来自真实列表。** 模块、环境、需求分支、文档分类都先查再选：
   `gws repo ls`、`gws env ls`、`gws ls`、`gws doc families`。
   不要凭印象写模块名，不要用近似拼写，不要“顺手”多加一个模块。
3. **先预览，再执行。** 下面这些命令不带执行开关时**只预览、不改任何东西**：
   `gws mr`、`gws rm`、`gws clean`、`gws revert`、`gws reset-remote`、
   `gws branch-prune`、`gws branch-rename`。
   必须先把预览结果给用户看，得到明确同意后再加 `--create` / `--yes` / `--force`。
4. **不替用户做有外部影响的事。** 不自动 `gws push`、不自动 `gws merge --push`、
   不自动提 MR、不自动删需求/分支。用户没明说，就先问。
5. **选填参数也问。** `--only` / `--exclude`、`--push`、`--rebase`、标题、分类、
   基线这类开关，执行前都要问一遍，并说明“不填时的默认行为”。
6. **代码只 `git add`，不 `commit`、不 `push`。** 提交由人 review 后执行。
7. **失败就停。** 报错通常已经写明下一步；不要用改名、重建、删目录绕过。

## 新建需求：字段必须与界面一一对应

界面「新建需求」的字段和约束如下。用 `gws new` 时按同一套来，**不要多填、不要乱填**。

| 界面字段 | 命令参数 | 规则 |
|---|---|---|
| 需求名称（中文名） | `--title` | 给人看的名字。**留空 = 分支名**，不要自己编一个中文名 |
| 分支名 | 位置参数 `<后缀>` 或 `--branch <完整名>` | 二选一，必填。后缀模式由工具拼 `<前缀>-<日期>-<后缀>`；用户已写日期时工具会自动去掉，不重复拼 |
| 需求分类 | `--category` | 可留空。**留空 = 按年月归组（如 `2026-10`）**，不要自己编分类名 |
| 模块 | `--modules a,b` | 可留空。**留空 = 只挂文档库，不拉任何代码**；要代码必须用户明确点名 |
| 基线来源 | `--from` | 可留空。缺省 `主干`；要基于别的需求时，只能用 `gws ls` 里存在的 `ws:<分支>` |
| 备注 / 自定义信息 | 无 | 命令行不支持；需要就让用户到界面里填，**不要塞进标题或分类** |

```bash
# 只写文档（最常见）：不写 --modules，默认就只挂文档库
gws new checkout-revamp --title "收银台改版"

# 要代码：模块名必须来自 gws repo ls，且用户明确说过
gws new checkout-revamp --title "收银台改版" --modules demo-payment,demo-api

# 完整分支名：不再自动拼前缀和日期
gws new --branch feature-20261021-checkout-revamp --title "收银台改版"
```

用户只给了一个中文需求名时，**把这张表逐项问完**（选填也问，并说清默认）：

> 1. 分支名：用「checkout-revamp」这个后缀可以吗？会建成 `feature-20261021-checkout-revamp`
> 2. 需求名称：就叫「收银台改版」，还是留空用分支名？
> 3. 分类：不填就按年月归到 `2026-10`，要指定别的分类吗？
> 4. 模块：不选就只挂文档库、不拉代码；需要哪个代码模块？
> 5. 基线：不填就用主干；要基于别的需求吗？

**先展示将要创建的分支名，再执行。** 不要先建出来再告诉用户建成了什么。

## 导入需求

```bash
gws get <远程分支> [--title "需求名称"] [--category 需求分类]
```

- `<远程分支>` 必须是远程**真实存在**的分支；不确定就先 `gws ls` 或问用户。
- 模块由工具自动识别，**不要手工补模块**。
- 导入前也要把「需求名称」「分类」问一遍：名称留空 = 用分支名；分类留空 = 按
  文档里已有的归类走。先说清默认，再执行。
- 分类留空时按文档里已有的归类走，不要另起一个。

## 其他界面动作 ↔ 命令

下表的命令都要**先问清该动作的选填项**（如合并要不要 `--push`、拉取用不用
`--rebase`、只处理哪些模块），说明“不填时的默认”，再执行。

| 界面动作 | 命令 | 必填 / 约束 |
|---|---|---|
| 加模块 | `gws add <模块>...` | 模块必须在 `gws repo ls` 里；只加用户点名的 |
| 移除模块 | `gws drop <模块>...` | 先确认模块确实在该需求里（`gws st`） |
| 合并到环境 | `gws merge <环境>` | 环境必须来自 `gws env ls`；默认只合本地，**不加 `--push`** |
| 拉别人提交 | `gws pull` | 有本地未提交改动时先问用户怎么处理 |
| 推送需求分支 | `gws push` | 有外部影响，**用户明确要求才执行** |
| 同步基线 | `gws sync-main` | 基线按 `.workspace.json` 的 `base` 链 |
| 提 MR | `gws mr` → `gws mr --create` | 先预览；细节见 `gws-merge-request` 技能 |
| 改分支名 | `gws branch-rename <新名>` | 先预览；完全未推送时不需要 GitLab 令牌 |
| 撤销未提交改动 | `gws revert` | 先预览，确认后 `--yes` |
| 回退到远程样子 | `gws reset-remote` | 会丢本地提交，必须用户明确同意 |
| 删除需求 | `gws rm <分支>` | 先预览风险；文档会归档，未推送内容会拦下 |
| 清理残留目录 | `gws clean` | 先预览，确认后 `--apply` |

## 命令参考

```bash
# hub / 仓库 / 环境
gws init <目录> [--envs dev,pre]
gws repo add <git地址>...
gws repo ls | rm <仓库名>...
gws env add <环境>...
gws env ls | rm <环境>...
gws sync

# 需求生命周期（在 ws/<分支>/ 内执行）
gws new [<分支后缀>|--branch <完整分支名>] [--title "名称"] [--category 分类] [--modules a,b] [--from 基线]
gws get <远程分支>
gws st                               # 各模块状态：改动 / vs远程 / vs主干
gws add <模块>...
gws drop [<模块>...]
gws ls
gws rm <分支>... [--force]
gws clean [--apply]

# 协作与合并
gws pull [--rebase]
gws push
gws merge <环境> [--push]
gws sync-main [--from <ref>]
gws done

# MR
gws mr                               # 预览
gws mr --create                      # 批量创建
gws mr --close                       # 关闭（不碰分支）

# 文档
gws doc attach [--category 分类] | new <类型> | ls | status | sync [--push] | families

# 危险操作（缺省只预览，加 --yes 执行）
gws revert
gws reset-remote
gws branch-prune
gws branch-rename <新名>

# 更新
gws update [--apply]
```

**所有模块级命令都支持 `--only a,b` / `--exclude a,b`。** 写错的模块名会直接报错，
不会静默什么都不做——这也意味着**不要拿它试错**，先看 `gws st`。

## 工作区约定

hub 靠 `.gws-hub` 向上定位，所有命令在 hub 内执行（或加 `--hub <路径>`）。

```
<hub>/
├── repos/<仓库>/           生产干净代码（主干镜像，只读）
├── envs/<环境>/<仓库>/      测试环境代码（只读）
├── ws/<分支名>/<仓库>/      需求目录（改代码只看这里）
├── repos/<文档库>/        文档库（特殊仓库：不可移除）
└── AGENTS.md / CLAUDE.md   AGENTS.md 是目录语义与编码约束；CLAUDE.md 只是指针
```

- **先读 hub 根目录的 `AGENTS.md`**（目录语义、改代码规则、提交约定都在里面）。
- 一个需求一个分支，分支名就是目录名；导入时目录名自动与远程分支一致。
- 需求中文名存在 `.workspace.json` 的 `title`；导入时从文档库读取。
- **文档库目录名从 hub 配置推导**（`gws hub show` 里的 `dochub_name`，取自你填的仓库地址，
  常见是 `doc-hub`、也可能是 `x-doc-hub`）—— 下面凡写 `<文档库>` 的地方都用它。
- 改代码只在 `ws/<分支>/` 下，`repos/` 与 `envs/` 的改动会被同步抹掉。
- 不要切分支：每个模块目录已固定在需求分支上。

## 分阶段需求（V2 基于未上线的 V1）

```bash
gws new 增长2期 --from ws:feature-260901-增长
gws sync-main
```

- `ws:<上游分支>` 必须真实存在（先 `gws ls`）。
- 上游没有该分支的模块会**自动降级主干**，不会整体失败。
- 基线可随时改 `.workspace.json` 的 `base`，之后 `gws sync-main` 按新值来。
- 界面上的「与基线」对比按配置链**倒序**解析（后配置的优先），上游不存在就往前退，
  全都没有才退回主干。

## 文档

文档统一在**文档库**上按需求分支管理（目录名见上面那条，下同）：

```
repos/<文档库>/workspaces/<需求分类>/<分支名>/
```

- **AI 产生的文档写 `ws/<当前分支>/<文档库>/workspaces/<分类>/<分支>/`**
- 分类留空时按年月（`YYYY-MM`）；V1/V2/bugfix 要放一起，就填与上一期相同的分类。
- 已并入主干的期次是**已归档历史文档**，只读，不要改。
- 只有工具生成的 `AGENTS.md` / `CLAUDE.md` / `meta.json` 的期次视为空文档，
  不要在列表里把它当成真实需求文档。

## 排查

```bash
gws ls && gws st                     # 先看现状
gws gitlab status                    # GitLab 连不上时先查这个
gws clean                            # ws/ 下有残留目录（先预览）
```

常见报错与下一步：

- 「分支已存在于远程」→ 这是别人的需求，用 `gws get`
- 「本地落后于远程」→ 先 `gws pull`
- 「该仓库没有 dev 分支」→ 正常，不是每个仓库都参与每个环境
- 「已推送，必须配 GitLab 令牌才能安全改名」→ 不要绕过，先让用户配 token 或确认
