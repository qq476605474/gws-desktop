# gws 设计方案

> 面向贡献者与二次开发者：这份文档说明**为什么这么设计**，以及哪些坑**不要再踩一遍**。
> 日常使用看 [使用教程](使用教程.md)。

---

## 0. 它解决什么

一个需求常常横跨七八个仓库：每个仓库开一个分支、切来切去、忘了推、合环境时漏了一个、
提 MR 时把主干名写错（`main` / `master` 混用）……

gws 把「一个需求涉及的所有仓库」收进**一个工作区（hub）**：

```
<hub>/
├── repos/<仓库>/        生产干净代码（主干镜像，只读）
├── envs/<环境>/<仓库>/   测试环境代码（分支可按仓库单独覆盖）
├── ws/<分支名>/<仓库>/   需求目录 —— 改代码只看这里
└── repos/<文档库>/      文档库（需求文档按分支管在这里；目录名取自你填的地址）
```

**全程不用切分支**：每个模块目录固定在自己的分支上，AI 与人看到的都是同一份。

## 1. 总体架构

### 1.1 约束

1. **`crates/core` 不依赖 Tauri、不依赖 clap。** 上层怎么用是上层的事。
2. **`crates/core` 不直接打印 stdout。** 所有操作返回 `serde::Serialize` 的结构化结果，
   由调用方决定渲染成文本还是 JSON。早期实现让前端正则解析 ANSI 彩色文本，
   是主要的脆弱来源，本版明确消除。
3. **依赖方向单向**：`cli` → `core` ← `src-tauri`。不允许反向。
4. **凭据与身份跟着 hub 走**，没有「全局配置」（见 §2.3）。

### 1.2 Crate 划分

```
crates/core/     全部领域逻辑，纯 Rust
├── hub/         hub 定位、初始化、配置（gws.json）
├── repo.rs      仓库管理：clone / 列出 / 移除
├── env.rs       环境：标识 ↔ 分支名解耦映射
├── workspace/   需求工作区生命周期
├── git.rs       **git 命令的唯一出口**
├── gitlab/      GitLab API 客户端 + 凭据
├── http.rs      极小的 HTTP 封装（JSON + 带进度下载）
├── dochub/      文档库集成
├── deploy.rs    发布地址矩阵（deployments.json）
├── update.rs    自更新（GitHub Releases）
└── gen/         临床细节：name / paths / date / progress / error

crates/cli/      gws 二进制（clap）
src-tauri/       桌面端外壳（薄壳，业务逻辑全在 core）
src/             Vue 3 + Naive UI 前端
skills/          给 AI 助手用的技能
```

### 1.3 为什么调 `git` 二进制而不是 `git2`

所有操作都要求与「人工在终端里敲 git 命令」**行为完全一致** —— 用户可能前脚用
gws 合了代码，后脚就在 IDE 里操作同一个 worktree。libgit2 在 `worktree`、
`merge --autostash`、`branch --unset-upstream` 等边缘语义上与 git 二进制存在偏差，
而这些恰恰是本工具的核心依赖。

`crates/core/src/git.rs` 是**唯一**调用 git 的地方，所有命令都经过它，因此
`core.quotePath=false`、`core.longpaths=true`、凭据注入、超时控制这些「不加就静默出错」
的东西只需维护一份。

## 2. Hub：目录与配置

### 2.1 目录语义

| 目录 | 是什么 | 代码状态 |
|---|---|---|
| `repos/<仓库>/` | 生产干净代码，各仓库的主干镜像 | `gws sync` 会 reset 到 `origin/<主干>`，**只读** |
| `envs/<环境>/<仓库>/` | 测试环境代码 | 跟随环境分支，由发布流程推进 |
| `ws/<分支名>/<仓库>/` | 需求目录，**改代码只看这里** | 各仓库固定在 `<分支名>` 上 |
| `repos/doc-hub/` | 文档库（特殊仓库，不可移除） | 已归档的历史文档在 `main` 上 |

标记文件 `.gws-hub` 用于向上定位 hub 根目录。**用独立的标记文件**是有意的：
新旧两版工具对 hub 的内部约定不同（`ws/` 下目录名、是否有 `docs/`、配置格式），
互相接管对方的 hub 会出错 —— 用不同标记，新版本走进旧 hub 时会直接报
「不在任何 hub 目录内」，而不是自信地做错事。

`repos/` 下的主 clone 是**唯一**存放 `.git` 的地方；`envs/`、`ws/` 下都是它的
worktree（`.git` 是文件）。这条约束带来一个有用的推论，见 §2.3。

### 2.2 `gws.json`

```jsonc
{
  "schema": 1,
  "name": "我的代码库",
  "gitlab": { "base_url": "https://gitlab.example.com" },  // 建 hub 时固定，不可改
  "git":    { "author_name": "张三", "author_email": "z@example.com" }, // 可留空
  "defaults": { "branch_date_digits": 8, "branch_prefix": "feature" },
  "envs": [{ "id": "dev", "label": "开发", "branches": {} }],
  "dochub": { "url": "https://gitlab.example.com/team/docs.git", "enabled": true },
  "quick_links": [{ "label": "打开发布页", "url": "https://deploy.example.com" }]
}
```

- 新增字段一律 `#[serde(default)]`，**不升 `schema`**：`check_version` 读到不同的版本
  会硬失败且没有恢复路径，升版本会让「还没绑定 GitLab 的 hub」连打开都过不去，
  补绑命令也就无从跑起。真正要表达的约束（地址非空）是**运行时闸门**。
- `quick_links` 为空 ⇒ 界面**整块隐藏**快捷入口，而不是摆一个点了 404 的按钮。
- 部署地址矩阵单独成文件 `deployments.json`（它常被批量编辑，跟结构性配置混在
  一起容易误改）。

### 2.3 凭据与身份：为什么都落在 hub 里

| 东西 | 位置 | 可改？ |
|---|---|---|
| GitLab 地址 | `gws.json` 的 `gitlab.base_url` | **建 hub 时固定，不可改** |
| 文档库地址 | `gws.json` 的 `dochub.url` | **建 hub 时固定，不可改** |
| GitLab token | `<hub>/gitlab-token`（0600） | 随时可换 |
| 提交身份 | `gws.json` 的 `git` + 各仓库 local config | 随时可改 |

**为什么不是全局一份**：同一台机器上常有多套身份与实例（公司 GitLab、个人 GitHub、
外包项目）。全局配置**必然串** —— 提交记录里会出现另一个身份，或者代码被推到
错误的实例上，而且事后极难发现。跟着 hub 走之后，「打开哪个 hub 就是哪套环境」
成为一条不需要解释的规则。

**地址不可改的两道闸门**（第二道是兜底，防止将来新增的修改路径绕过第一道）：

1. `Hub::bind_gitlab` 首行就拒绝二次绑定；
2. `HubConfig::save` 写盘前与磁盘上的既有值比对，不一致直接拒绝。

**token 允许被环境变量覆盖**（`GWS_GITLAB_TOKEN` > `GITLAB_TOKEN` > hub 凭据文件）：
CI / 脚本 / 临时换账号需要显式传参赢过持久值。**但地址不认环境变量** ——
否则「地址不可改」就形同虚设。

### 2.4 提交身份：为什么不每次命令带 `-c`

hub 里的 worktree 与主 clone **共享同一份 local config**（实测：worktree 的
`--git-common-dir` 指向主仓库 `.git`，且 `extensions.worktreeConfig` 未开启，
所以 `git config --local` 读写的正是主仓库那一份）。于是：

- 每个仓库只需设**一次**，它的全部 worktree（`ws/`、`envs/`）自动继承；
- **用户在 `ws/` 里手工 `git commit` 用的也是这个身份** —— 这才是「读到错误身份」
  的真正来源，只在工具自己执行的命令上加 `-c` 是挡不住的。

`git::apply_identity` 在身份被清空时会**删除** local config 里的旧值：
只删不写是必须的，否则之前设过的身份会继续生效，用户改了配置却看不到变化。

## 3. 核心领域模型

| 概念 | 是什么 |
|---|---|
| **仓库**（repo） | 登记进 hub 的 git 仓库，在 `repos/` 下有一份主干镜像 |
| **环境**（env） | 一批仓库在某个分支上的组合；标识与分支名**解耦**（可给单个仓库覆盖分支） |
| **需求**（workspace） | 一个分支名 + 一组模块；每个模块是 `ws/<分支名>/<模块>` 的 worktree |
| **文档**（doc） | 每个需求在文档库里的一个期次目录，按分支管理 |
| **基线**（base） | 需求从哪儿长出来：主干，或 `ws:<上游分支>`（分阶段需求，可多条做优先级链） |

需求元数据在 `ws/<分支名>/.workspace.json`（`SCHEMA = 2`），含中文名、模块、
基线、分类、备注、自定义信息。

**创建需求是事务性的**：先预检全部模块（仓库在不在、分支是否已被占用、本地有无
同名残留、基线是否存在），全部通过才动手 —— 失败时不留下半残工作区。

## 4. GitLab 集成

### 4.1 客户端

`gitlab::Client` 是自研的薄封装（只用到 projects / users / branches / merge_requests
四组接口，约两百行）。不引第三方 `gitlab` crate 的原因：自建 / 私有实例的版本
往往落后于官方 SaaS，第三方 crate 按最新 API 演进，遇到旧版本字段缺失会在
反序列化时炸掉，而那种错误现场极难排查。

因此响应结构体里**所有字段都给 `#[serde(default)]`**：缺字段不能让整个请求失败。

构造入口只有 `Client::for_hub(&Hub)`（地址与 token 都取自 hub）与
`Client::anonymous`（公开读取）。**没有 `from_env`** —— 那正是「凭据不跟 hub 绑定」
的根源。

### 4.2 仓库来源白名单

`gitlab::check_remote(remote, allowed_host)` 校验仓库地址的主机是否等于
**当前 hub 绑定的** GitLab 主机（`allowed_host` 由调用方传入，不再是写死的常量）。

要拦的是「从别的远端拉代码进来」：混进来之后工具的所有假设都不成立（分支约定、
MR、文档库都只对那个实例有效）。**本地路径一律放行**（离线镜像、自建的临时仓库、
测试里的裸仓库都走这种形式），拦掉它们只会逼人绕过校验。

### 4.3 MR

`resolve_reviewers` 有三级优先级，**没有内置默认评审人**：

```
命令行 --reviewer / --frontend-reviewer / --backend-reviewer
  > 需求级 <工作区>/.gws-mr.json
  > 全局 ~/.config/gws/reviewers.json
```

三层都没配就是「本次不提评审人」。配置文件损坏只告警并降级到上一层（一个写错的
JSON 不该让人连 MR 都提不了）；但命令行指定的 username 非法时**直接报错中止** ——
那是本次操作的显式意图，静默忽略会让人以为生效了。

目标分支**绝不写死**：`main` → `master` → 查 `origin` HEAD 逐个探测（各仓库主干名
不统一是真实存在的）。

## 5. doc-hub 集成协议

文档库就是一个**普通 git 仓库**，只是被特殊对待（置顶、不可移除）：

- 主 clone：`repos/doc-hub`；需求里的 worktree：`ws/<分支>/doc-hub`
- 文档目录：`workspaces/<需求分类>/<分支名>/`
- 每个期次目录带 `meta.json` + `AGENTS.md`（`CLAUDE.md` 只是指向它的指针）

**「期次是否已归档」只看内容在不在主干的树里**（`git ls-tree <主干> -- workspaces/`），
不看 `git branch --merged` —— 后者对「还没有自己提交」的分支平凡成立，会把正在写的
文档判成已归档（见 §8 第 19 条）。

## 6. 前端

Vue 3 + Naive UI + Pinia。分层：

- `src/bridge.ts` 是**唯一**碰 `invoke` 的地方 —— 命令名/参数名写错只需改一处
- `src/lib/` 放纯函数（目录解析、表单规则、分组），因此可在 vitest 里直接测
- `src/components/` 与 `src/views/` 只做渲染与交互

**长操作走 `bg()`**：会联网 / 会起子进程的 Tauri 命令必须 `async` + `bg()`
（`spawn_blocking` + `catch_unwind`），否则要么卡住界面几十秒，要么在 debug 构建下
直接 panic（见 §8 第 16、17 条）。

---

## 7. 危险操作框架

`revert` / `reset-remote` / `branch-prune` / `branch-rename` 这类会丢东西的操作，
一律**默认只预览**，加 `--yes` 才执行。预览与实际执行共用同一份 plan 结构，
所以「预览里看到的」就是「会做的」。

删除类操作**必须删除后校验**目标是否真的消失（见 §8 第 11 条）。

## 8. 必搬踩坑清单

这套行为是照着**已经在真实使用中打磨过的一版实现**重写的，下面这些坑都是那版实际
踩出来的。每一条在 Rust 侧都有对应实现，实现里也留了注释 —— 改动前先读这一节，
别把踩过的坑重新踩一遍。

| # | 坑 | 这版怎么处理 |
|---|---|---|
| 1 | `merge --autostash` 回填 stash 冲突时 git **仍返回 0**，只能靠 `diff --name-only --diff-filter=U` 判断 | 统一用 unmerged 路径判定，不看退出码 |
| 2 | 有 `MERGE_HEAD` = 合并冲突（stash 暂存在 `MERGE_AUTOSTASH`）；无 = 回填冲突 | 同上，两类分别提示 |
| 3 | `merge-base --is-ancestor origin/$env HEAD` 可检测远程被 force push 重建 | 镜像类分支（envs）的失效检测 |
| 4 | 从 `origin/main` 建分支时 git 自动设 upstream → **必须 `branch --unset-upstream`**，否则 IDE Push 推向主干 | `new`/`add` 后强制解除 |
| 5 | 动手前必须 `worktree prune`，否则 `worktree add` 撞"已存在"路径 | 所有 worktree 操作前的固定前置 |
| 6 | envs reset 失败时，**仅当"无本地改动 且 无未推送提交"**才自动重建，否则保留现场交给人 | 保守自愈策略 |
| 7 | sync 需**双向统计** `fwd`/`bwd`，才能识别"远程回退/强推"而非报 0 | 变更摘要要能表达"回退" |
| 8 | base 链解析：逐个来源检查该模块是否有对应分支，首个命中即基线，**全部不命中兜底主干** | 基线优先级解析 |
| 9 | `rename` 必须**先读全元数据再 mv**（mv 后旧路径失效） | 顺序敏感 |
| 10 | 嵌套 hub 会让向上查找产生歧义 → `init` 时拒绝 | hub 定位 |
| 11 | `rm_one` 的 `rm -rf` **无错误检查却无条件报成功** ← 那版最典型的 bug | **修正**：删除后校验 + 如实报告（§6.1 #6） |
| 12 | Windows 下目录软链会失败或静默退化成拷贝 | Rust 用 junction 处理，或干脆不用软链（文档库直接定址） |
| 13 | 空数组展开在旧 shell 下报 unbound | Rust 无此问题，但**空 modules / 空 envs 的边界要有测试** |
| 14 | `gws doc ls` 在工作区异常时会以 exit 0 返回 hub 级列表（首行退化为 `docs`） | 结构化输出后此怪癖消失 |
| 15 | 预检全部模块通过才动手，失败整体回滚，不留半残工作区 | `new` 的事务性语义 |

### 8.1 本版新增的平台级坑（不是旧实现的，实现中踩到，同样必须记住）

| # | 坑 | 症状 | 应对 |
|---|---|---|---|
| 16 | **`reqwest::blocking` 在 debug 构建下不能跑在 tokio 运行时里** | `tauri dev`（debug）下任何联网命令必 panic：`Cannot drop a runtime in a context where blocking is not allowed`。命令体炸在 spawned 任务里，**没有任何响应回给前端**，`invoke` 的 Promise 永不 settle → 界面**永远转圈**。CLI 没有 tokio 运行时，所以 CLI 一直是好的 | 所有会阻塞（联网 / subprocess）的 Tauri 命令一律走 `commands::bg()`（`spawn_blocking` + `catch_unwind`）。**不要把 `#[tauri::command(async)]` 直接加在同步函数上**。`commands/tests.rs` 有回归测试钉住 |
| 17 | **Tauri 的同步命令跑在主线程上** | 一条同步命令里做 `git fetch` 或打 GitLab，会把界面卡住几十秒 | 会联网 / 会 fetch 的命令必须 `async` + `bg()`，即使它"看起来"只是查一下 |
| 18 | **git 默认转义非 ASCII 路径**（`core.quotePath`） | `ls-tree` / `status` 输出里中文目录名变成 `"workspaces/\347\247\201..."`，按 `/` 切分解析会**静默**全错 | 涉及路径解析处一律加 `-c core.quotePath=false`（`dochub::sync` 与 `archived_in_main` 都踩过） |
| 19 | **`git branch --merged` 对"没有自己提交"的分支平凡成立** | 刚建出来、还没提交的期次分支与主干同提交 → 被判成"已归档"，正在写的文档被标成只读 | 判"内容在不在主干的树里"（`ls-tree <主干> -- workspaces/`），见 §4.7 |
| 20 | **`canonicalize` 的逐字前缀（`\\?\`）要在**每一处**剥** | `checked_dir` 剥了、里面那次"防穿越"的比较忘了剥 → Windows 上逐字路径与剥过的 `dir` 一比 `starts_with` 必然为假：**只要文件真的存在，读它必报「路径越界」**（实测反馈：对比代码里点任何一项都这样）。同一个坑这是第三次（克隆、worktree add、browse） | 收成一个 `join_inside` / `resolved_inside`，所有"目录 + 相对路径"都走它；`starts_with` 是**纯词法**比较，所以还**先挡 `..` 与绝对路径**（见下表第 22 条） |
| 21 | **`git status` 默认把未跟踪的目录折成一行** | 输出 `?? workspaces/`（带尾斜杠）——那是目录不是文件，界面上却把它当一条"新增改动"列出来，点开读不出内容 | 改动列表用 `--untracked-files=all`（`status_lines(true)`）展开成一个个真实文件；点到目录也要给一句人话而不是报错 |
| 22 | **`Path::starts_with` 不做规范化** | `dir/../../../etc/hosts` 在"文件不存在 → `canonicalize` 失败"时会**通过**前缀检查（成分逐段对得上）。文件存在时会被 canonicalize 抓到，但不该把安全性押在"那个文件碰巧不存在"上 | `join_inside` 先拒掉含 `..` / 绝对路径 / 盘符前缀的入参 |
| 23 | **多阶段操作每段都发一个 `Start` 进度事件** | 用户点了「后台运行」把遮罩收起来，下一段（如导入需求里的"补环境"）又发 `Start` → 遮罩自己弹回来，看着像**一直弹框**（实测反馈） | `busy.dismissed`：`Start` 只在用户没选过「后台运行」时才重新显示；`dismissed` 只在新一轮操作开始时清掉 |

## 9. 分发与自更新

- **CLI**：`install.sh` 从 GitHub Releases 取二进制，校验「可执行文件魔数 + sha256」，
  按平台与架构选资产（选不到就明确报错，不猜）。
- **桌面端**：macOS dmg / Windows nsis / Linux deb，同样挂在 Release 上。
- **自更新**：`update.rs` 打 GitHub API，与 hub 绑定的 GitLab **完全解耦** ——
  它下的是本软件自己的安装包，跟用户在哪个 GitLab 上管代码毫无关系。
  校验链：tag 必须是 `vX.Y.Z` → 按平台选资产 → 下载到**同目录**临时文件
  （跨文件系统 rename 不是原子的）→ 校验 sha256 → 防降级 → 原子替换。
  **任何一步失败都不改动现有二进制**：更新失败最坏的结果是「还是旧版」，
  而不是「二进制损坏、工具跑不起来」。
- **技能同步**：桌面端自带同版本的 CLI 与 `skills/`，启动时同步到本机**已安装**的
  AI CLI 目录（没有的目录不新建）；改过的技能先备份成 `*.gws-backup`，本机版本
  更新时不降级。

## 10. 明确不做的事

- **不做多用户 / 服务端**：仍是单机 CLI + 桌面端。
- **不预设任何仓库、发布系统、评审人**：每个人的环境都不一样，预设等于替用户做决定。
- **不做静默兼容**：结构版本不认识就报错，配置缺必填项就报错并给出下一步命令。
  错误信息必须能指导下一步（`gws gitlab bind …` / 界面上的对应入口）。
- **不代用户提交代码**：AI 在这个 hub 里只能 `git add`，`commit` / `push` 由人 review
  后执行 —— 这条写进每个 hub 的 `AGENTS.md`。
