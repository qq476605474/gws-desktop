# 使用教程

面向第一次用「GWS」的人。**照着一节一节做就行**，不需要先懂它的设计。
想了解为什么这么设计，看 [`设计方案.md`](设计方案.md)。

- 这是什么：多仓库需求开发管理 —— **拉代码、合环境、提 MR、写文档**
- 一个需求 = 一个工作区，只放这次会改的仓库，各仓库都停在同一分支上，**全程不用切分支**

---

## 1. 装

从 [Releases 页](https://github.com/qq476605474/gws-desktop/releases) 下对应平台那个包：

| 你的系统 | 下这个 |
|---|---|
| macOS（Apple Silicon / M 系列） | `gws-desktop_x.y.z_aarch64.dmg` |
| Windows 64 位 | `gws-desktop_x.y.z_x64-setup.exe` |
| Linux（Debian / Deepin） | `gws_x.y.z_amd64.deb` |

**装完程序名是「GWS」。**

- **macOS**：包**没有签名**，首次打开要 **右键 → 打开**（直接双击会被拦）。
  或者执行一次：`xattr -dr com.apple.quarantine /Applications/GWS.app`
- **Windows**：安装包文件名是英文，装进去是中文名。双击一路下一步即可。
- **Linux**：`sudo dpkg -i gws_x.y.z_amd64.deb`，然后从开始菜单打开
  （包名必须是 ASCII，所以叫 `gws`，菜单里显示的是中文名）。

命令行版是同一批文件里的 `gws-*`，放到 PATH 里即可，用法见第 7 节。

## 2. 第一次：建 hub、加仓库

**hub 是统一管所有仓库和需求的根目录**，比如 `~/Documents/my-hub`。建议放在容量足的本地盘。

1. 打开程序 → 「新建 hub」→ 选父目录、起个名字
   - 填齐**三样**：**GitLab 地址**、**Personal Access Token**（在 GitLab 的
     「用户设置 → 访问令牌」里创建，勾 `api` 权限）、**文档库地址**
     （一个普通的 git 仓库，需求文档按分支存在里面；没有就先建个空仓库）
   - 点「测试连接」确认能连上 —— 地址写错或 token 无效现在就看得出来
   - ⚠️ **地址与文档库地址创建后就不可改了**（它们是「哪些仓库能纳管」和文档
     挂载位置的依据）；token 之后可以随时在「设置 → GitLab」里换
   - 环境默认建 `dev`；需要 pre 就勾上
2. 创建时会先连一次 GitLab 校验地址与 token，**通过之后才建目录** ——
   校验不通过时磁盘上什么都不会留下
3. **不预设任何仓库**：建完到「仓库」页按需添加（支持从 GitLab 检索你有权限的仓库）
4. 已经建过 hub 的其他人，选「打开已有 hub」，指向那个目录就行

> 📌 **进 hub 先看根目录的 `AGENTS.md`**（程序自动生成并保持最新，是目录语义地图和
> 给 AI 的编码约束）。`CLAUDE.md` 只是一句指针「请先阅读同目录 AGENTS.md」——
> Claude Code 认前者、Codex / Cursor 认后者，内容只维护一份，不会再出现两份不同步。
> 你自己也值得扫一眼：**同一个仓库在 hub 里有好几份副本，用途完全不同**。

## 3. 日常流程（重点就这一段）

```
新建需求 → 改代码 → 推送 → 合到环境 → 提 MR → 并入主干
```

### 3.1 新建需求

「需求」页 → 新建：填**需求名称**（给人看的中文名），需要改代码时再勾**这次会改到的仓库**
（不确定就少勾，之后能加）。

- **默认只勾文档库**：不选代码仓库时不会拉任何代码，只建需求目录和文档目录。
  只写方案/需求文档时保持默认即可
- 分支名两选一：**分支前缀组合**（先选分支前缀，再填分支后缀，拼成
  `分支前缀-日期-分支后缀`）或**完整分支名**。
  选后者时「分支后缀」那一栏不会出现，不必填
- 组合模式下**后缀里不用再写日期**：写了 `20261020-xxx` 也会被去掉，最终只有一个日期。
  预览下方若出现黄字「后缀里的日期已忽略」，说明它帮你去了重
- 需求目录是 `ws/<分支名>/`，**分支名 = 目录名**，一次定死（没推送也可以改名，见 §7）
- **需求分类**留空时按年月归组（如 `2026-10`）；要把同一需求的几期放一起，
  填上一期相同的分类名

### 3.2 改代码

在 IDE 里打开 `ws/<分支名>/<仓库>/`。**只在 `ws/` 下改** —— `repos/` 和 `envs/` 都是镜像，
改动会被下一次同步抹掉。

用 AI 写代码时**让它也只在 `ws/` 下改**（hub 的 `CLAUDE.md` 里写死了这条）。

### 3.3 推送

需求详情 →「推送」。

合到环境**只认远程分支** —— 没推的话合不进去（这是有意设计，避免把别人拉不到的代码合进测试环境）。

### 3.4 合到环境验证

需求详情 →「合并到环境」（选 dev / pre）。

- 想合完直接推上去（别人就能看到），用「**合并到环境并推送**」
- 冲突时它会列出冲突的模块和文件路径，去那些文件里解决完，**再点一次同一个按钮**即可

「**合并到环境检查**」用来看合完的结果：哪些模块进环境了、推没推、有没有残留冲突。

代码进环境验证没问题后，点「**发布**」—— 里面是**灰度版 / 正式版发布页**两个入口
（「发布页」这个工具自身也有两套，类似软件有灰度/正式；**不是**要发布的目标环境，
两个页面功能完全一样）。进去以后 dev、灰度、正式**所有环境都能选**。
点完新页面打开，弹窗随即关闭（跟「总览」页的快捷入口是同一份配置）。

### 3.5 提 MR（合主干）

需求详情 →「MR」标签页 → 点「提 MR」→ 先看预览（每个模块的目标分支、评审人、改动量），
确认无误再创建。

- **标题和描述可以改**：默认标题是 `需求上线-需求名`，描述是固定模板；
  改过之后按你写的**原样提交**，没改的字段留空就用默认值
- 各仓库主干名 `main` / `master` 混用，程序**逐个探测**，不会提错
- 前后端评审人自动分配，可以改。**哪个模块算前端**看两条：模块名以 `-front` 结尾，
  或在 `gws.json` 的 `defaults.frontend_groups` 里列出的 GitLab group 下
  （默认只认后缀；group 名各家不同，所以不预设任何值）
- 建完会给你一份**能直接粘到群里的清单**（含 MR 链接和 @人）

### 3.6 收尾

「并入主干检查」确认全部已并 → 删除需求。只有**删了会丢东西**才会拦：
未提交改动，或既没推送也没进主干的提交；已合进主干、远程源分支被删掉的不会拦。

## 4. 拉别人的需求

其他人推了分支，你这边**不要自己新建同名需求**，用「需求」页的**拉取**（`gws get <远程分支>`）：
它会自动识别这个需求涉及哪些仓库，把工作区建出来。

标准协作节奏：

```
开工前先拉（需求详情 →「拉取」）→ 改代码 → 推送 → 合环境
```

推送/合并前程序会检查你是否落后于远程，落后会**中止**并提示先拉 —— 免得用旧代码覆盖其他人的成果。

## 5. 分阶段需求（V2 基于还没上线的 V1）

新建需求时把**基线**填成上游需求的分支（如 `ws:feature-260901-增长`）。之后同步也走这个基线。

**需求分类**（新建时的高级项）决定文档归到哪个分类目录下：同一需求的二期/三期填同一个分类名；
**不填就按年月归组**（如 `2026-10`），不会去猜已有的分类。

上游某个仓库没有这个分支时**自动降级到主干**，不会整体失败。上游上线后想切回主干，把基线改成主干即可。

**「对比代码」默认是「与本地」**：比的是工作区里**还没提交**的改动，所以分支还没推送
也能看。已经提交到分支的内容用「与主干」看；推送之后「与远程」看的是"本地有、远程还没有"的全部内容。

**「与基线」对比**：需求详情的文件浏览器里，除了「与主干」「与远程」等，多了一个
「与基线」——它按需求的实际基线链**从后往前**找（后配置的优先，不按分支名日期猜），
上游分支已经删掉/从来没推过就逐个往前退，全都没有才退回主干。界面上会直接显示
解析到的 `origin/<分支>`，降级时会注明「已退回主干」。

## 6. 文档

文档统一在**文档库**上按需求分支管理（它就放在 `repos/` 下，是个普通仓库）：

```
repos/<文档库>/workspaces/<需求分类中文名>/<分支名>/
```

> 文档库的**目录名来自你建 hub 时填的仓库地址**（`x-doc-hub.git` → `x-doc-hub`），
> 不一定是 `doc-hub`。下面凡写 `<文档库>` 的地方都用它；确切名字看设置页或 `gws.json`。

- **正在写的文档**：在需求里写，路径 `ws/<当前分支>/<文档库>/workspaces/...`
- **已并入 main 的期次 = 已归档的历史文档**，只读，**不要改**（它是当时的事实记录）
- 同一个需求的 V1 / V2 / bugfix 归在同一个需求分类目录下，按日期排序
- 「文档」页可以按分支看每期的文档树与日期；**只有工具生成的 `meta.json` / `AGENTS.md` /
  `CLAUDE.md` 的空期次不会列出来**，本地打不开的期次（只在远程分支或环境 worktree 里）
  也不列，需求详情里会明确写「该需求没有需求文档」
- 期次是不是已归档，看它**有没有并入 main**（不存在单独的「状态」字段了 —— 以前那个
  手写状态既不维护也不可信）

用 AI 写文档时，让 AI 写进当前需求那份（`AGENTS.md` 里也写了这条）。

## 7. 命令行（gws）

界面能做的事命令行基本都有，脚本化/批量时更顺手。

```bash
# 仓库与环境
gws init <目录> [--envs dev,pre]   # 建 hub
gws repo add <git地址>...          # 加仓库（会自动检出到各环境）
gws env add <环境>...              # 加环境
gws sync                          # 同步主干与所有环境

# 需求
gws new [<分支后缀>|--branch <完整分支名>] [--modules a,b] [--from 基线] [--title "需求名称"] [--category 需求分类]
                                   # 不写 --modules 时只挂文档库（与界面默认一致）
                                   # 不写 --category 时按年月归组（如 2026-10）
gws get <远程分支>                 # 拉别人的需求
gws ls | gws st                    # 列出需求 / 看各模块状态
gws add <模块>... | gws drop [<模块>...]
gws rm <分支>... [--force]

# 协作与合并
gws pull [--rebase]                # 拉别人推到同一分支的提交
gws push                           # 推送本需求所有仓库
gws merge <环境>                   # 合到本地环境（不推）
gws merge <环境> --push            # 合并到环境并推送
gws sync-main [--from <ref>]       # 把基线的最新代码合进来（长周期防冲突）
gws done                           # 检查是否已全部并入主干

# MR
gws mr                             # 预览
gws mr --create                    # 创建
gws mr --close                     # 关闭（不删分支）

# 文档
gws doc new <类型> | ls | sync [--push]

# 危险操作（默认只预览，确认后加 --yes）
gws revert | gws reset-remote | gws branch-prune | gws branch-rename <新名>
```

> **改分支名**：完全没推送时是**纯本地操作**，不需要 GitLab 令牌；
> 只要有一个模块已经推到远程，就会要求配置 token，走「先推新分支、确认、再删旧分支」，
> 不会静默只改一半。已有 MR 的源分支不会自动改，需要到 GitLab 上处理。

**所有模块级命令都支持 `--only a,b` / `--exclude a,b`** —— 有时只想动某几个项目。
模块名写错会直接报错，不会静默什么都不做。

常见提示怎么处理：

| 提示 | 怎么办 |
|---|---|
| 「分支已存在于远程」 | 那是别人的需求，用「拉取」 |
| 「本地落后于远程」 | 先拉取 |
| 「该仓库没有 dev 分支」 | 正常 —— 不是每个仓库都参与每个环境 |

## 8. 桌面端界面在哪找什么

| 页面 | 干什么 |
|---|---|
| **总览** | 一眼看全部：哪些需求没合完、环境落不落后、待办 |
| **需求** | 需求列表与详情。详情里是**所有操作**：拉取 / 推送 / 合并到环境 / 合并到环境并推送 / 合并到环境检查 / 并入主干检查 / MR / 派发Paseo任务 / 危险操作 |
| **仓库** | 「仓库」标签管仓库地址与本地目录，每行能配**自定义信息**（Jenkins 链接、常用域名等）、看**详情**（各环境访问地址、被哪些需求/环境用着）；「环境」标签看各环境检出了什么、改分支覆盖 |
| **文档** | 按需求分支看文档树（空期次自动隐藏）；**提交并上传文档**在需求详情的「需求相关文档」弹窗里 |
| **帮助** | 内置的精简版使用说明，离线可看 |
| **设置** | 主题、用哪个终端打开、**用编辑器打开**（默认 IDEA，可换其它编辑器或自定义命令）、GitLab token（含**申请个人密钥的直达链接**）、桌面端/CLI/Skills 三个版本、自动同步与更新 |

三个容易忽略但好用的地方：

- **仓库的自定义信息**：仓库页每行的「自定义信息」。配**链接**（如 dev/prod 的 Jenkins）
  会直接显示在列表里，点一下就打开；配**纯文本**（如模块域名）点一下是**复制**。
  各环境的**访问地址**（点开站点、复制域名）在同一行的「详情」里编辑，那份配置还能整份
  「导出配置」发给别人。
- **环境页的「未检出」**：环境表里显示的是**配置**（该检出什么），目录要等同步才建出来。
  还没检出的行会标「未检出」并置灰 —— 点「同步此环境」就好。
- **用编辑器打开**：每个「打开目录」旁边都有。默认 IntelliJ IDEA，项目已经开着时会直接
  切到对应窗口；换编辑器在「设置 → 用编辑器打开」，列表里没有的写自定义命令
  （`{path}` 会替换成目录）。

## 9. 合错代码怎么处理

如果某次合并**把环境搞错了**（不该进的合了进去 / 该合的没合上 / 留下冲突残留），
可以在环境目录里**就地改**：

```bash
cd <hub>/envs/<环境>/<仓库>
git log --oneline -5      # 先看清现状，确认要撤的正是那笔
# 改完
git add -A && git commit -m "撤掉误合进来的 xxx"
```

边界（**这条被写进 `CLAUDE.md`，AI 也照这个来**）：

- **只处理合错本身** —— 需求本身的改动一律回 `ws/<分支名>/` 去改
- 在环境分支上写需求代码会让环境和需求分支**分叉**，两边再也对不上
- 改完**告诉人**动了哪个仓库/分支，**推送由人执行**（推上去就等于改了测试环境）

**让 AI 来改也可以**：这是 AI「能改 `envs/`」的唯一例外，其余情况它只在 `ws/` 下动手。

## 10. 让 AI 用上这套工具（技能）

仓库的 `skills/` 下有一个技能，装到 Claude Code 里 AI 就知道怎么操作 hub：

| 技能 | 用途 |
|---|---|
| `gws` | 工作区 / 需求 / 环境 / MR / 文档的完整说明，以及 AI 在这个 hub 里的行为约束 |

安装方式：跑一遍 `install.sh` 就会把 CLI 装到 `~/.local/bin/gws`，并把技能
同步到本机**已安装**的 AI CLI 各自的 skills 目录：Claude Code `~/.claude/skills`、
OpenCode `~/.config/opencode/skills`、Qoder CLI `~/.qoder/skills`、Codex
`~/.codex/skills`；没有的目录不新建（每个目录写 `.gws-version`，设置页据此显示版本；
`GWS_NO_SKILLS=1` 可跳过）。只动这个技能目录，不碰别人的技能。

技能开头写的是**执行纪律**：所有字段先问用户（选填也要说明“不填用默认”）；模块 / 环境 / 分类 / 评审人必须来自
`gws repo ls`、`gws env ls`、`gws ls` 等真实输出；`gws new` 的默认值与界面一致
（不写模块就只挂文档库、分类留空按年月）；危险操作先预览再确认。目标是 AI 在界面上
能做的那几个动作，用法和结果都跟界面一致，不产生脏数据。

**桌面端会自动同步**：桌面端自带**同版本**的 CLI 与这三个技能。安装或升级桌面端后，
启动时会自动覆盖本机旧版本 —— CLI 放进已经在用的那个位置（一个都没有就装到
`~/.local/bin`），技能写进本机已安装的 AI CLI 目录（Claude Code / OpenCode /
Qoder CLI / Codex），没有的目录不新建。被改过的技能会先备份成
`SKILL.md.gws-backup`；本机版本比桌面端**新**时保留、不降级；版本号相同但内容不同
（重新构建的同版本 SNAPSHOT）也会更新。
设置页有「同步 CLI 与 Skills」，随时可以手动再跑一次。

### AI 会话（Paseo）：需求内派发 / 全局自由会话

需求详情**顶部**有 **「派发Paseo任务」**。点开后先弹窗选 provider（`paseo provider ls`
里可用且启用的排成一列，默认第一个，**必须选**），确认后会在 **hub 根目录**启动一个
[Paseo](https://paseo.sh) 会话，标签页标题默认用**需求名称（需求描述）**，开场说明只有
一行（当前分支 + 直接开始），并自动打开 Paseo 桌面端。

左下角还有 **「开 AI 会话」**（不绑定需求）：

- 适合**建需求前先聊清需求**，或直接让 AI 查线上日志；查出是 bug 再回「需求」页建一个来修
- 弹窗里可以填**会话标题**，留空叫「临时会话」；provider 同样必选
- 两种会话共用同一个 Paseo 工作区与环境（hub 根目录），只是标签页不同
- 首次会自动把 hub 根目录注册成 Paseo 项目（已注册就跳过），Paseo 桌面端里能看到它
- 工作区会**复用同一个**（名称就是 hub 目录名，如 `my-hub`），每次只是新开一个标签页；
  你自己命名的工作区（如「查日志」「需求开发」）不会被占用
- 工作目录是 **hub 根**，不是 `ws/<分支>` —— 这样 AI 读得到根目录的 `AGENTS.md`，
  也能看到 `repos/` 里的主干代码。开场说明不罗列要读的文件，AI 会按 `AGENTS.md`
  自己去找；也不要求它复述你已知的信息
- 需要本机已安装 Paseo，且 `paseo` 在 PATH 或 `~/.local/bin` 里；找不到时会直接提示
- **Windows**：在 Paseo 桌面端「集成」→「CLI 文档」→「命令行」里安装 CLI，
  会装到 `%USERPROFILE%\.local\bin\paseo.cmd`；`npm install -g @getpaseo/cli` 则装到
  `%APPDATA%\npm\paseo.cmd`。两个位置本工具都会找，装完**重启本应用**即可
- **ARM 版 Windows**（含 Parallels / VMware 里的 Windows 11 ARM）：Paseo 桌面端要下
  **arm64** 安装包（`Paseo-Setup-<版本>-arm64.exe`）；x64 包在 ARM 上可能装不上。
  也可以直接用 `npm install -g @getpaseo/cli`，CLI 本身不分架构
- provider 列表为空通常不是工具的问题：每个 provider 需要先在 Paseo 里装好对应
  CLI 并登录（如 Claude Code / Codex），`paseo provider ls` 里显示可用且启用才会出现

**外部改完不刷新？** Paseo 是另一个应用，桌面端收不到通知。切回桌面端窗口时会自动
刷新需求列表、打开着的需求详情和文档页；窗口一直没离开过时，点「需求」页右上角的
**「刷新」**。

## 11. 常见问题

**Q：装完打开提示「已损坏」或打不开？**
macOS 没签名。右键 → 打开，或执行第 1 节里那条 `xattr` 命令。

**Q：加完仓库 / 建完环境，环境页还是空的？**
正常情况下会自动补齐。如果某几行显示「未检出」，点「同步此环境」即可。

**Q：合并到环境时提示要先推送？**
合并只从 `origin/<你的分支>` 拉。先推送。

**Q：GitLab 令牌去哪申请？**
设置页 GitLab 卡片里有「去申请 Personal Access Token」按钮，直接跳到当前 GitLab 的
令牌页；勾 `api` 权限即可。

**Q：点「派发Paseo任务」提示找不到 paseo？**
先装 Paseo；已经装了的话确认 `paseo` 在 PATH 或 `~/.local/bin/paseo`。
Windows 上是 `paseo.cmd`：在 Paseo 的「集成」→「CLI 文档」→「命令行」里安装，
落在 `%USERPROFILE%\.local\bin`；npm 全局装在 `%APPDATA%\npm`。
装好后重开桌面端再点一次即可。

**Q：弹窗说「没有可用的 provider」？**
说明 paseo 找到了，但里面没有既可用又启用的 provider。先在 Paseo 里装好并登录
对应的 CLI（Claude Code / Codex 等），再运行 `paseo provider ls` 确认。

**Q：桌面端会覆盖我改过的 skill 吗？**
会 —— 安装/升级桌面端时按「一起自动覆盖」处理。覆盖前原文件会备份成
`SKILL.md.gws-backup`；如果本机版本比桌面端新，则保留不降级；版本号相同但内容变了也会更新。

**Q：左上角版本号旁边出现「有新版本」？**
点它就能看更新内容并一键更新；平时它只安静地显示当前版本（在 hub 名字下面）。

**Q：能只同步某几个仓库吗？**
能，所有模块级操作都支持 `--only`；界面上在同步弹窗里勾选。

**Q：换电脑了怎么办？**
新电脑建/打开同一个 hub（或只建空 hub），再用「拉取」把需求一个个拉回来。

**Q：GitLab 连不上？**
设置页 → GitLab → 「重新检测」看具体错误。token 需要 `api` 权限。
